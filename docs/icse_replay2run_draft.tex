\title{Planning-Guided Replay for Repository Environment Construction}

\begin{abstract}
Executable repository environments are a prerequisite for evaluating software engineering agents.
Benchmarks for issue resolution, test generation, and repository execution assume that a repository can be installed, built, and tested in a reproducible environment.
Recent work such as Repo2Run formulates this task as automated Docker environment construction for real repositories.
However, current LLM-based build agents often solve the task through unstructured trial and error: they repeatedly install packages after import failures, mix environment configuration with source-code edits, and finally synthesize a Dockerfile from a noisy interactive trajectory.
This behavior creates two failures.
First, the agent may spend many steps in an error-driven installation loop instead of following dependency evidence from manifests and lock files.
Second, a sandbox that was eventually configured successfully may not replay as a fresh Docker build because the trajectory contains failed commands, diagnostic probes, runtime-only commands, and order-sensitive state changes.

This paper presents \tool, a planning-guided framework for repository environment construction.
\tool introduces a read-only \planner that explores the repository and sandbox before setup, extracts a \ttg of runtime, package-manager, dependency, build, service, environment-variable, and verification requirements, and materializes an ordered todo-list for the build agent.
The graph is validated and updated as execution succeeds or fails, giving the build agent a persistent plan artifact rather than a one-shot prompt hint.
\tool further addresses reproducibility with replay-aware trajectory compression and a bounded Dockerfile repair loop.
Trajectory compression reduces long setup histories while preserving successful state-changing commands, exact package/version evidence, and final verification evidence.
Dockerfile repair validates the generated Dockerfile in a fresh build-and-test loop and edits only the Dockerfile, using structured trajectory evidence to restore omitted or misordered setup commands.

We frame two central research questions for ICSE evaluation: whether typed planning improves repository environment construction success, and whether the planning loop reduces unplanned error-driven dependency installation.
The current artifact snapshot contains 420 Repo2Run result files, with 379 successful executable environments and an overall pass rate of 90.24\%.
On a rerun set of 52 previously failing instances, the current planning-enabled pipeline produced 12 successful Docker builds and 11 executable environments.
These results are preliminary and not yet a causal ablation; they motivate the full experimental design, which will compare the full system against variants without typed planning, without plan updates, without replay-aware compression, and without Dockerfile repair.
\end{abstract}

\section{Introduction}

Software engineering research increasingly depends on executable repositories.
Benchmarks for issue resolution, program repair, test generation, and autonomous coding agents require more than source code.
They require a runtime in which dependencies can be installed, tests can be collected, and repository-specific assumptions can be reproduced.
This requirement is difficult at scale.
Real repositories combine Python packages, native libraries, optional platform markers, local services, generated assets, package-manager quirks, and undocumented setup steps.
Manual Dockerfile authoring does not scale to hundreds of repositories, and naive automated setup often fails for reasons that are outside the source code itself.

Repo2Run recently framed this problem as automated construction of executable environments for code repositories~\cite{hu2025repo2run}.
Given a repository, an agent explores an environment, installs dependencies, diagnoses failures, and produces a Dockerfile.
The setting is compelling because it moves repository execution from a manual packaging task to an agentic software engineering task.
At the same time, our experience with Repo2Run-style pipelines shows that environment construction is not merely a sequence of shell commands.
It is a planning and replay problem.

The planning problem appears before the first setup command.
An LLM build agent that starts directly from a shell often follows the shortest visible error.
If \texttt{pytest} reports \texttt{ModuleNotFoundError: x}, the agent installs \texttt{x}; if the next run reports \texttt{ModuleNotFoundError: y}, it installs \texttt{y}.
This loop can make progress on simple repositories, but it fails when the real dependency solution is encoded in \texttt{pyproject.toml}, lock files, CI configuration, platform markers, or package-manager constraints.
It also blurs the boundary between environment repair and code repair.
Installing a missing package, setting \texttt{PYTHONPATH}, or modifying dependency metadata may be legitimate environment configuration.
Creating source stubs, rewriting tests, or patching repository semantics usually invalidates the environment-building task.

The replay problem appears after the sandbox succeeds.
An interactive sandbox trajectory is not a Dockerfile.
The trajectory contains successful installs, failed installs, diagnostic probes, repeated file edits, service starts, runtime-only commands, and final verification commands.
Some failed commands leave partial side effects.
Some successful commands are read-only and should not enter the Dockerfile.
Some repeated file patches are necessary because a later reinstall overwrites an earlier patch.
As a result, a sandbox can reach a state where \texttt{pytest --collect-only} succeeds, while a synthesized Dockerfile built from the same trajectory fails in a fresh image.

This paper presents \tool, a framework that treats repository environment construction as planning-guided replay.
\tool has three main mechanisms.
First, a read-only \planner inspects repository evidence and the target sandbox environment before setup.
It extracts a \ttg whose nodes represent runtime, system package, package manager, install strategy, language dependency, project build, service, environment variable, asset, runtime command, and verification requirements.
The graph is validated, topologically sorted, and rendered as an ordered todo-list for the build agent.
The plan is materialized as both JSON and Markdown inside the host logs and the sandbox, so the build agent can inspect the current plan at any point through a dedicated plan-view action.
The plan is not immutable.
Execution feedback updates node status, promotes fallback edges when observations contradict the initial plan, and returns the next todo item to the build agent.

Second, \tool uses replay-aware trajectory compression.
Long trajectories must be reduced before they can be passed to an LLM synthesizer or repair agent, but generic compression can remove replay-critical information.
\tool therefore preserves successful state-changing commands as separate chronological units, keeps exact package names and versions, records file edits, and keeps final verification evidence.
Read-only probes and repeated failures can be grouped, but they cannot erase the setup actions that explain the final sandbox state.

Third, \tool validates and repairs Dockerfiles through fresh replay.
After the initial Dockerfile is generated, the benchmark runner performs a fresh Docker build and runs the verified test command in a new container.
If build or test replay fails, a bounded repair agent receives the Dockerfile, fresh failure logs, and the structured trajectory evidence.
The repair agent may edit only the Dockerfile and is instructed to restore omitted or misordered setup commands before inventing a new setup strategy.

The paper targets the following research questions:

\begin{description}[labelwidth=3em,leftmargin=4em,align=left]
  \item[RQ1:] Does typed planning improve repository environment construction success?
  \item[RQ2:] Does the planning loop reduce unplanned error-driven dependency installation?
  \item[RQ3:] How much do replay-aware trajectory compression and bounded Dockerfile repair contribute to fresh replay success?
  \item[RQ4:] What failure modes remain after planning, compression, and repair?
\end{description}

This draft reports the current artifact snapshot as preliminary evidence.
The repository currently contains 420 Repo2Run result files, of which 379 are successful executable environments, corresponding to a 90.24\% overall pass rate.
For a focused rerun of 52 previously failing instances, the planning-enabled pipeline achieved 12 Docker build successes and 11 executable environments.
These numbers are useful as a progress indicator, but they are not yet sufficient for causal claims.
The ICSE-ready evaluation will add controlled ablations for typed planning, dynamic plan updates, replay-aware compression, and Dockerfile repair.

This paper makes four contributions:

\begin{itemize}[leftmargin=*]
  \item We formulate repository environment construction as a planning-guided replay problem, separating environment configuration from source-code repair and separating sandbox success from Dockerfile reproducibility.
  \item We introduce a \planner that extracts, validates, materializes, and dynamically updates a \ttg for repository setup.
  \item We propose replay-aware trajectory compression that reduces setup histories while preserving state-changing commands, package/version evidence, and final verification.
  \item We implement bounded Dockerfile repair over fresh build/test failures and outline an evaluation protocol for measuring planning quality, error-driven installation behavior, and replay success on Repo2Run.
\end{itemize}

\section{Background and Motivation}

\subsection{Repository Environment Construction}

Repository environment construction aims to create a runtime in which a target repository can be built and tested.
For Python repositories, Repo2Run uses pytest collection as a primary readiness signal: the collection command should execute without collection, import, or configuration failures.
This target differs from requiring all tests to pass.
Assertion failures may reflect repository bugs or benchmark-specific expectations, whereas collection failures usually indicate environment problems such as missing dependencies, invalid package versions, absent native libraries, or wrong test configuration.

Repo2Run-style evaluation commonly reports two metrics:

\begin{itemize}[leftmargin=*]
  \item \dgsr, Dockerfile Generation Success Rate: the generated Dockerfile builds successfully.
  \item \ebsr, Environment Building Success Rate: the built image can execute effective test collection or test execution.
\end{itemize}

\subsection{Why Direct Agent Setup Fails}

LLM agents are effective at local diagnosis because they can run commands and react to errors.
However, a direct ReAct loop~\cite{yao2023react} gives the model a local view of the last observation.
In environment construction, that local view can be misleading.
A missing-import traceback is often a symptom rather than a dependency plan.
The repository may specify an extra, a lockfile may pin a compatible version, CI may install a system package first, or a platform marker may exclude a dependency on Linux.
Without an explicit plan, the agent may stack packages one at a time until version conflicts accumulate.

The absence of a plan also weakens task boundaries.
Environment construction should allow changes that make the environment faithful to the repository's intended setup: installing packages, selecting a base image, setting variables, editing dependency metadata, or configuring test paths.
It should not allow arbitrary source or test rewrites that make tests collect by changing repository semantics.
A build agent needs this boundary at execution time, not only in the initial prompt.

\subsection{Why Sandbox Success Does Not Guarantee Dockerfile Success}

A successful sandbox is an interactive final state.
A Dockerfile is a replay program.
The gap between the two is the central source of fresh replay failures.
Figure~\ref{fig:replay-gap} shows a simplified example.
The agent patches an installed package, later reinstalls the package, and patches it again.
The final sandbox succeeds.
A synthesizer that deduplicates repeated patches may remove the second patch, but the reinstall has overwritten the first patch.
The Dockerfile fails even though the sandbox trajectory contained a successful solution.

We observed five recurring hazards.
Read-only probes such as \texttt{pip index versions} can fail in Docker builds despite being useful during exploration.
Failed compound commands can leave partial state.
Package-manager commands can be order-sensitive.
Runtime commands, such as service starts, may be needed before tests but inappropriate during image build.
Output truncation commands such as \texttt{head} or \texttt{tail} can hide the real failure from later synthesis.
\tool addresses these hazards by making planning and replay evidence explicit.

\section{System Overview}

Figure~\ref{fig:architecture} summarizes \tool.
The system receives a repository instance and produces a Dockerfile plus evaluation artifacts.
Its workflow has five stages:

\begin{enumerate}[leftmargin=*]
  \item The \planner collects repository evidence, probes the host and sandbox environment, selects a base image, and generates a \ttg.
  \item The build agent executes setup actions in the sandbox while consulting the materialized plan and receiving plan updates.
  \item The controller records a structured evidence ledger containing successful actions, failed actions, test attempts, and final verification evidence.
  \item The synthesizer compresses the trajectory and creates a replay-oriented build recipe and Dockerfile.
  \item The benchmark runner performs fresh build/test validation and invokes bounded Dockerfile repair when replay fails.
\end{enumerate}

\section{Planning Agent}

\subsection{Design Goals}

The \planner is a read-only pre-execution module.
It does not install dependencies, run tests as setup, start long-lived services, or modify repository files.
Its purpose is to turn repository evidence into an execution map.
Three design goals shape the module.

\textbf{First, planning should be evidence-driven.}
The module reads manifests, lock files, setup files, CI configuration, pytest configuration, import statements, and platform markers before the build agent reacts to individual traceback messages.
For Python projects, this encourages a manifest-first dependency strategy.
The planner prefers dependencies implied by project metadata, lock files, requirements files, setup scripts, and CI setup before installing arbitrary packages one by one.

\textbf{Second, planning should distinguish execution environments.}
The planning host may be macOS on arm64, while the target runtime is a Linux Docker container on amd64.
The \planner records both the host environment and the sandbox runtime environment.
This distinction helps prevent host-specific assumptions, such as macOS-only dependencies or architecture-specific wheels, from being treated as target requirements.

\textbf{Third, planning should persist beyond the initial prompt.}
A one-shot paragraph in the build agent prompt is easy to ignore after several observations.
\tool writes the plan as JSON and Markdown files inside the host logs and the sandbox.
Inside the sandbox, these files are stored under \path{/tmp} and share the \path{repo2run_environment_plan} prefix.
The build agent can issue \texttt{\_\_VIEW\_PLAN\_\_} to inspect the current graph, todo-list, risk notes, and fallback plan.
After each relevant action, the controller updates node status and returns a short plan digest.

\subsection{Typed Task Graph}

The \ttg is the core planning artifact.
It contains typed nodes, typed edges, risk notes, unresolved questions, an ordered todo-list, and fallback actions.
Nodes have the following types:

\begin{itemize}[leftmargin=*]
  \item \texttt{runtime}: language version, operating system, architecture, and base-image requirements;
  \item \texttt{system\_package}: native libraries and OS packages;
  \item \texttt{package\_manager}: pip, poetry, conda, npm, or other package tools;
  \item \texttt{install\_strategy}: an install mode such as targeted dependencies, editable install, extras, or lockfile-constrained install;
  \item \texttt{language\_dependency}: Python or language-level dependencies;
  \item \texttt{project\_build}: build steps such as editable installation or asset generation;
  \item \texttt{service}: external services or daemons needed for tests;
  \item \texttt{env\_var}: required environment variables;
  \item \texttt{asset}: datasets, generated files, or local resources;
  \item \texttt{runtime\_command}: preparation commands that should run before verification;
  \item \texttt{verification}: test collection or execution commands.
\end{itemize}

Edges encode ordering and requirement relations.
Representative edge types cover runtime requirements, package-manager use, strategy-before-dependency, dependency-before-build, build-before-verification, runtime-preparation-before-verification, and verification-after-runtime constraints.
Edges can be hard or soft.
Hard edges constrain the topological order.
Soft edges express likely preferences and can be promoted when execution feedback confirms them.

Each node and edge carries evidence, confidence, and optional command hints.
Command hints are advisory.
They are not proof that a command should enter the final Dockerfile.
Only successful sandbox actions and verified setup evidence can become replay commands.

\subsection{Read-Only Planning Loop}

The \planner performs a small loop of read-only probes.
The first round collects deterministic evidence: runtime files, dependency manifests, lock files, pytest configuration, and import candidates.
Later rounds are conditional.
If imports suggest undeclared dependencies, the planner performs a focused import scan.
If a Poetry project contains platform-specific packages, the planner derives an install strategy that avoids full lockfile installation when it would pull macOS- or Windows-only dependencies into a Linux sandbox.
If the project exposes service or environment-variable requirements, the planner records them as risk notes and todo items.

The loop is intentionally limited.
It can inspect files and execute safe diagnostic commands through a sandbox inspection interface, but it cannot mutate the environment.
This boundary matters because planning should not consume the same setup budget as the build agent or contaminate replay evidence.

\subsection{Plan Materialization and Updates}

The build agent receives the plan through two channels.
First, the system prompt includes a compact planning context with the next todo item, high-risk constraints, and the path to the full plan file.
Second, the full plan is materialized in JSON and Markdown.
The action \texttt{\_\_VIEW\_PLAN\_\_} returns the current plan state.

After the build agent runs a command, the controller checks whether the command advances a planned node.
Successful planned steps mark nodes as completed or partially completed.
Failures can promote fallback edges and regenerate the ordered todo-list.
For example, if a manifest-first install strategy fails because a platform-specific package cannot be installed on Linux, the graph can promote a fallback targeted-dependency strategy.
The next observation then includes a plan update, which reduces the chance that the build agent continues down an outdated branch.

\subsection{Environment-Only Boundary}

The planner and build agent enforce an environment-only boundary.
The build agent may install packages, set variables, configure \texttt{PYTHONPATH}, edit dependency metadata, or adjust repository configuration files such as \texttt{pyproject.toml}, lock files, requirements files, \texttt{setup.cfg}, \texttt{tox.ini}, and \texttt{pytest.ini}.
These files define how the environment is built.
The agent should not create source stubs, rewrite tests, or patch application semantics simply to make collection pass.
This distinction is important for ICSE evaluation because otherwise the system could succeed by changing the program under test rather than building its intended environment.

\section{Replay-Aware Trajectory Compression}

The build agent's trajectory can exceed the context budget of later synthesis and repair steps.
However, ordinary summarization is unsafe for replay.
If compression hides a successful install, removes an exact version, or merges two order-sensitive file edits, the generated Dockerfile may fail.
\tool therefore uses a replay-aware compression schema.

The schema separates trajectory content into three classes.
Read-only inspections and repeated failed attempts may be grouped into concise blocks.
Successful state-changing actions remain explicit single-step blocks.
Final verification commands and their effective-test evidence remain explicit.
The compressor is also instructed to preserve package-manager identity, exact package names and versions, installed and already-satisfied package lists, generated files, file edits, warning/error messages that explain dependency choices, and chronological order.

This objective differs from general trajectory reduction work such as AgentDiet~\cite{xiao2025agentdiet}.
The goal is not only to reduce token cost.
The goal is to produce a compressed artifact from which a Dockerfile can be replayed.
For that reason, \tool allows a compressed summary to keep more information than a minimal natural-language summary would keep.
Replay fidelity is preferred over brevity when the two conflict.

\section{Dockerfile Synthesis and Repair}

\subsection{Build Recipe Synthesis}

The synthesizer converts the compressed trajectory and evidence ledger into a structured build recipe:

\begin{lstlisting}[basicstyle=\ttfamily\small]
{
  "build_commands": [...],
  "runtime_preparation_commands": [...],
  "test_commands": [...],
  "excluded_commands": [...],
  "rationale": "...",
  "confidence": "high|medium|low"
}
\end{lstlisting}

Build commands become Dockerfile \texttt{RUN} instructions.
Runtime preparation commands run inside the container immediately before tests when their effects are ephemeral, such as starting a service.
Test commands are the final verified commands.
Excluded commands record read-only diagnostics, failed attempts, or commands whose effects should not be replayed.

The synthesizer follows a conservative replay rule: preserve successful persistent setup actions unless there is clear evidence that the command is read-only, test-only, runtime-only, or non-replayable.
This rule makes generated Dockerfiles less elegant, but it reduces the risk of losing state that made the sandbox work.
When the LLM returns invalid recipe JSON, deterministic fallback logic extracts successful persistent setup commands and renders a replay-first Dockerfile.

\subsection{Fresh Replay Validation}

The benchmark runner validates the generated Dockerfile in a fresh Docker context.
It records build stdout, build stderr, timeout status, test stdout, test stderr, runtime preparation commands, and the final execution status.
This step is part of the method, not a post-hoc check.
It is the only way to know whether the synthesized Dockerfile reproduces the sandbox.

\subsection{Bounded Dockerfile Repair}

If fresh replay fails, \tool invokes a bounded Dockerfile repair agent.
The repair agent receives the current Dockerfile, fresh build/test logs, \texttt{agent\_run\_summary}, the build recipe, successful actions, failed actions, and the verification bundle.
It must output a complete replacement Dockerfile as JSON.
It may not edit repository source files outside Dockerfile commands.
It is instructed to restore omitted successful setup commands, preserve original command order, avoid unrelated setup strategies, and keep the base image unless the logs show that the base image is the failure cause.

This design keeps repair tied to evidence.
An unconstrained repair agent could repeat the same unplanned trial-and-error behavior as the original setup agent.
The bounded repair agent instead treats failure logs as feedback about the replay program.
Its preferred fix is to make the Dockerfile match the successful sandbox trajectory more faithfully.

\section{Implementation}

\tool is implemented in Python.
The top-level controller constructs an \texttt{EnvironmentPlanningAgent}, obtains an initial plan before sandbox execution, refines it with read-only sandbox exploration, and writes the current plan to both host logs and the sandbox.
The ReAct-style planner prompt includes the planning context, the environment-only boundary, the manifest-first dependency rule, and the plan-view action.
During setup, the controller updates the plan after command success or failure and injects a compact plan digest into later observations.

The \planner contains six main components:
\begin{itemize}[leftmargin=*]
  \item repository evidence collection for manifests, lock files, CI files, pytest configuration, and import statements;
  \item base-image planning, which replaces the earlier standalone image selector and records image evidence inside the plan;
  \item host environment probing before sandbox creation;
  \item bounded read-only sandbox exploration;
  \item graph validation for typed nodes, typed edges, references, and ordering constraints;
  \item graph updates that promote fallback plans and recompute todo-lists from execution feedback.
\end{itemize}

Trajectory handling is split across online and offline compression.
During the ReAct loop, long observations can be safety-compressed or LLM-compressed before being returned to the planner.
After setup, the system creates a setup-log summary for Dockerfile synthesis.
Both compression stages preserve package/version details, real errors, test evidence, and successful state-changing commands.

The benchmark runner integrates Dockerfile generation, fresh replay validation, and repair.
It loads the Repo2Run dataset, executes the agent, validates Docker build and test execution, writes per-instance artifacts, and records aggregate \dgsr and \ebsr metrics.

\section{Evaluation}

\subsection{Research Questions}

The final ICSE evaluation will answer four questions:

\begin{description}[labelwidth=3em,leftmargin=4em,align=left]
  \item[RQ1:] Does the \ttg improve \dgsr and \ebsr compared with a build agent that receives no typed plan?
  \item[RQ2:] Does the planning loop reduce unplanned error-driven installation behavior?
  \item[RQ3:] How much do trajectory compression and Dockerfile repair contribute to fresh replay success?
  \item[RQ4:] What categories of failures remain?
\end{description}

\subsection{Dataset and Metrics}

We use the 420-instance Repo2Run benchmark~\cite{hu2025repo2run}.
Each instance specifies a repository and target commit.
Following Repo2Run, we measure \dgsr and \ebsr.
\dgsr counts instances for which the generated Dockerfile builds successfully.
\ebsr counts instances for which the built image executes an effective test collection or test execution command.

For RQ2, \dgsr and \ebsr are not enough.
We will measure planning behavior directly:

\begin{itemize}[leftmargin=*]
  \item plan consultation rate: number of \texttt{\_\_VIEW\_PLAN\_\_} actions and automatic plan digests per instance;
  \item planned-step completion rate: fraction of completed setup actions matched to graph nodes;
  \item manifest-backed dependency ratio: fraction of dependency installs justified by manifests, lock files, CI, or planned fallback nodes;
  \item error-driven install count: number of dependency installs justified only by the immediately preceding import error;
  \item diagnostic waste: repeated failed probes, output-truncation commands, and commands rejected by the sandbox guard;
  \item plan revision count: number of graph/todo updates triggered by execution feedback.
\end{itemize}

\subsection{Planned Ablations}

The ICSE submission needs controlled ablations before making strong claims.
We plan the following variants:

\begin{itemize}[leftmargin=*]
  \item \textbf{No typed plan.} The build agent receives the standard prompt and repository context, but no \ttg, plan files, or plan-view action.
  \item \textbf{Static plan only.} The build agent receives the initial typed plan, but execution feedback does not update node status or todo order.
  \item \textbf{No planning probes.} The graph is built from repository files only, without host/sandbox environment probes.
  \item \textbf{No replay-aware compression.} Dockerfile synthesis receives raw or generic-compressed trajectory evidence.
  \item \textbf{No repair.} The system stops after the first generated Dockerfile fails fresh replay.
  \item \textbf{Full \tool.} Typed planning, dynamic updates, replay-aware compression, fresh validation, and bounded repair.
\end{itemize}

For each variant, we will report \dgsr, \ebsr, token cost, wall-clock time, plan metrics, and failure categories.
The key causal tests are whether typed planning improves success and whether plan updates reduce error-driven installs.

\subsection{Failure Analysis Protocol}

Remaining failures will be manually classified into:

\begin{itemize}[leftmargin=*]
  \item incomplete dependency plan;
  \item platform-specific dependency conflict;
  \item native/system package failure;
  \item package-manager solver failure;
  \item source/test semantic modification blocked by environment-only guard;
  \item missing service, environment variable, or asset;
  \item Dockerfile replay gap;
  \item Docker infrastructure or network failure;
  \item no effective test signal.
\end{itemize}

For RQ2, we will also classify install commands by evidence source: manifest/lock/CI-backed, plan-fallback-backed, traceback-only, or unrelated.
This classification directly tests whether the planning loop reduces unplanned error-driven installation.

\section{Discussion}

\subsection{What Planning Changes}

The \planner changes the build agent's role.
Without planning, the agent must infer the repository's dependency structure while reacting to shell output.
With planning, the agent receives an explicit graph, a next todo item, risk notes, and a fallback plan.
This does not remove the need for exploration.
Repository environments are incomplete and sometimes contradictory.
However, planning can make exploration more directed: the agent should first execute manifest-backed dependency strategies, then validate with tests, then promote fallback paths when observations contradict the graph.

This shift is important for ICSE because it gives the system measurable internal structure.
The plan can be inspected, validated, updated, and evaluated.
Instead of only asking whether the final Dockerfile works, we can ask whether the agent followed planned dependencies, whether it ignored platform-specific risks, and whether failed actions caused rational plan revisions.

\subsection{Why Repair Is Still Needed}

Planning improves setup, but it does not solve replay by itself.
Even a well-planned sandbox can contain order-sensitive actions that are hard to synthesize into a Dockerfile.
Fresh replay validation and Dockerfile repair therefore remain necessary.
The repair agent serves a different role from the build agent.
It does not explore the repository.
It repairs a concrete replay program using fresh failure logs and the recorded setup evidence.

\subsection{Limitations}

The current implementation is strongest for Python repositories.
The \ttg schema is language-agnostic, but many evidence collectors and verification heuristics are Python-specific.
The preliminary numbers are not yet an ablation study.
They show that the current pipeline can solve many instances and recover some prior failures, but they do not isolate the effect of typed planning, compression, or repair.
The final paper should include repeated runs or cache-control procedures because package indexes and network state can drift over time.

\section{Threats to Validity}

\textbf{Internal validity.}
The current preliminary results combine multiple output artifacts and do not isolate individual components.
The planned ablations are needed before attributing success to typed planning, trajectory compression, or repair.
LLM behavior may also vary across model versions.
We will report prompts, model identifiers, and per-instance logs.

\textbf{Construct validity.}
\ebsr measures whether tests can be collected or executed, not whether all tests pass.
This matches the environment construction goal, but it does not prove functional correctness.
The RQ2 metrics for error-driven installation require careful annotation rules so that manifest-backed fallback installs are not misclassified as traceback-only installs.

\textbf{External validity.}
Repo2Run focuses on Python repositories.
The approach should transfer to other ecosystems, but Node.js, Java, Rust, and multi-service repositories require additional evidence collectors and verification targets.

\textbf{Reliability.}
Docker builds depend on network availability, package indexes, base-image state, and architecture.
\tool records host environment, sandbox environment, selected base image, command logs, build logs, and test logs to support reproduction.

\section{Related Work}

\textbf{Repository environment construction.}
Repo2Run introduced automated Docker environment construction for repository execution at scale~\cite{hu2025repo2run}.
\tool follows the same high-level benchmark target but adds typed preplanning, plan updates, replay-aware trajectory compression, and bounded Dockerfile repair.

\textbf{LLM agents for software engineering.}
ReAct combines reasoning and acting for tool-using language models~\cite{yao2023react}.
SWE-agent shows that agent-computer interfaces can improve automated software engineering performance~\cite{yang2024sweagent}.
SWE-bench evaluates issue resolution on real GitHub repositories~\cite{jimenez2024swebench}.
These systems rely on executable environments.
Our work targets that prerequisite rather than issue patch generation.

\textbf{Trajectory reduction.}
AgentDiet studies trajectory reduction for lowering LLM agent cost~\cite{xiao2025agentdiet}.
\tool also compresses trajectories, but its compression objective is replay preservation.
Successful state-changing commands and verification evidence are preserved because they define the Dockerfile synthesis target.

\textbf{Containers and reproducibility.}
Docker containers are widely used to package software environments~\cite{merkel2014docker}.
Repository environment construction requires more than using Docker as a runtime.
The challenge is to infer a correct Dockerfile from incomplete repository evidence and a noisy interactive setup trajectory.

\section{Conclusion}

This paper presents \tool, a planning-guided replay framework for repository environment construction.
The central claim is that environment setup agents need both an explicit plan before execution and replay evidence after execution.
The \planner extracts and updates a \ttg that guides the build agent away from unplanned error-driven installation.
Replay-aware trajectory compression and bounded Dockerfile repair then turn the successful sandbox trajectory into a Dockerfile that can be validated in a fresh build.
The current artifact snapshot shows a 90.24\% pass rate across 420 Repo2Run result files and 11 recovered executable environments among 52 previously failing instances.
The next step is a controlled ablation study that isolates typed planning, dynamic plan updates, trajectory compression, and Dockerfile repair.
