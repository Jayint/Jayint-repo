The contribution is DIAGNOSIS (which layer/root cause owns this symptom), not RESOLUTION (Z3 does that, behind the graph) and not cross-repo MEMORY (out of scope).

## DESIGN — ANGLE B — CAPABILITY SATISFACTION model. Reframe the failure-scoped dependency graph from a flat fault ledger (Failure/Need/Provider/Attempt) into an AND/OR satisfaction tree whose ROOT is the single thing the agent actually cares about — "the real test run passes" — and whose interior is Capability nodes carrying an explicit three-valued satisfaction state (UNKNOWN / PROVEN / REFUTED). A Capability is satisfied iff its sub-capabilities (AND) and at least one of its candidate providers (OR) are satisfied; satisfaction propagates bottom-up. The graph is no longer "a list of things that went wrong" but "a proof obligation tree for environment readiness," and a Failure is demoted from a first-class node to EVIDENCE that flips one Capability to REFUTED. Z3 stays strictly behind it: each version-feasibility AND/OR subtree (pip closure consistency) is delegated to the existing Z3DependencySolver; its sat/unsat is just the satisfaction value of one Capability, and its unsat_core becomes a `conflicts_with` cross-link inside the tree. The central paper question this angle answers: does the AND/OR formalism buy MORE evaluability and explainability than the flat schema, or does it over-formalize? Verdict argued below: it is a net win for explainability and evaluability for THIS domain because environment readiness genuinely IS a satisfaction problem (every leaf is provable by a check_command and every interior is a Boolean combinator), but it over-formalizes if pushed to full propositional generality — so we constrain it to a typed, bounded, single-root tree-with-conflict-cross-links, not an arbitrary circuit.

## DESIGN — PARSIMONY + explainability. Thesis: a paper reviewer should grasp the entire representation in 30 seconds, so the graph carries the fewest types that still answer the five operational questions an environment-repair agent asks every turn: What failed? What does the env need? What is the real (lower) root-cause need? Who can provide it? What was tried, and did it work? I keep exactly the four codex nodes (Failure, Need, Provider, Attempt) but justify each against deletion; I collapse the codex 'Probe' into a check field on Need (a probe is not an entity, it is how you prove a Need); and I refuse to add any layer/manager node. The cross-layer property (pip / import-naming / system-native / interpreter / solver-conflict) is encoded as an ENUM FIELD on Need and Provider, not as extra node kinds. The conflict family is the one place I add an edge, not a node: Need--conflicts_with-->Need. Net: 4 node types, 5 edge types. Everything richer (concrete versions, transitive closure, the SAT model, unsat math) lives BEHIND the graph inside Z3 and is summarized into Provider/Attempt nodes, never exploded onto the agent-facing surface.
