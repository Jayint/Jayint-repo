### Change 1 — residual give-up only on host-grounded divergence; don't classify success events  (`54d892a`)
- **Observation:** memU-server & pyads gave up `planner_giveup` on **cycle 1** with the closure installed + a snapshot created. Adversarial root-cause (opus, refuted shim/config alternatives): their preserved `action_ledger` had exactly ONE event — the emit-drain's **successful** `pip install` (`rc=0`). `_runtime_ingest_phase` fed that success to the LLM classifier (prompted to explain a *failure*), which returned a non-env verdict → `note_out_of_scope` → `_out_of_scope` non-empty. With the closure drained (`partition().emittable == ()`), `(diverged or _out_of_scope) and not emittable` was True → `_residual_giveup` set → give-up fired at `orchestrator.py:290` **before `next_decision` / the discover-task ever ran**. `diverged` was empty (`found == []`); the give-up was driven purely by an LLM claim about a success.
- **Why:** Runtime feedback is a **failure** classifier — classifying a *successful* command is the bug. And an LLM-only `_out_of_scope` must never finalize the run (give-up is a *negative* finalization; host-owns-truth says no LLM-declared/action-implied finalization). The give-up must be host-grounded (`diverged` = residual mapping to a host-certified SATISFIED node, spec §8) and must not preempt the discover-task sufficiency loop.
- **What changed (`src/envstate/orchestrator.py`, `_runtime_ingest_phase`):**
  - Edit 2 (root removal, line 202): `obs = [(e.cmd, e.stdout) for e in new_events if e.rc != 0]` — never hand succeeded events to the failure classifier.
  - Edit 1 (defense-in-depth, line ~258): give-up now requires `diverged and not scheduler_frontier(new_graph) and not partition(new_graph).emittable` — dropped LLM-only `_out_of_scope` as a sole trigger; added the empty-`scheduler_frontier` guard so it can't preempt actionable agent work. No `done_flag` write, no gate weakened.
- **Verification:** Two behavioral tests added to `tests/test_residual_handler_wiring.py` (`..._success_event_does_not_give_up_on_cycle1`, `..._out_of_scope_without_divergence_does_not_finalize_giveup`). Confirmed **RED against pre-fix `15799d5`** (`assert 'planner_giveup' != 'planner_giveup'`) → **GREEN post-fix**. Adjacent suites 14 passed (residual/runtime_feedback/graph_scheduler/runtime_divergence); orchestrator sweep 19 passed.
- **E2E (partial, verify-postfix-v1gsp on rtpin_pilot5, b934412):** **memU-server pre-fix not-executed/gave-up (0.0) → post-fix executes, honest pass_rate 0.838 (83/99), eval status=success** (16 failures are genuine app/test failures e.g. `test_temporal_workers`, not env; `finalize: accepting majority-pass run (ratio=0.838)` is host-grounded pytest, ≥0.8 → real success). **pyads pre-fix gave-up → post-fix reaches `planner_done`** (premature give-up gone) but still `error` on a repo-specific build failure (next blocker, see below). websockets+ingestr in flight; radical baseline still running. ### Change 2 — don't score the repo's own Dockerfile when agent configuration failed (anti-laundering)  (`f4179bf`)
- **Observation:** ingestr's eval built a malformed Dockerfile with `RUN go run ./cmd/genregistry`. Adversarial root-cause (opus, reproduced BYTE-FOR-BYTE; my first backslash-join hypothesis was REFUTED after I checked it against ground truth): ingestr **failed to configure** (`configuration_success: False`, `build_recipe: null`, 0 genregistry/--mount in 42 recorded actions). On config-failure the agent writes NO `workplace/Dockerfile`; the eval adapter (`multi_docker_eval_adapter.py:825-826`) read it **unconditionally** and silently fell back to the **repo's OWN upstream multi-stage Go Dockerfile** left in the clone, then `_extract_agent_dockerfile_instructions` (keeps only `RUN`-prefixed lines across BOTH `FROM` stages, drops continuation bodies, keeps dangling `\`) mangled it → exit 100. Decisive repro: fetching ingestr's live upstream Dockerfile through the real extractor yields the exact 6 malformed instructions.
- **Why:** scoring a failed run against the repo's own Dockerfile is **hollow-success laundering** (for ingestr it broke; for a repo whose own Dockerfile *passes* it would fake a win). Host owns truth → a failed configuration must fail honestly. The fix must be ARM-NEUTRAL (must not skip genuinely-successful runs in v1gsp OR radical).
- **What changed:**
  - `agent.py`: `self.configuration_success` init default in `__init__` + set as the first line of `_write_run_summary` (3221) — the sink BOTH arms call (v1 1394, legacy/radical `finally` 2066), so it's arm-neutral. (Verified: `run()` returns the flag only on the v1 path; radical's `run()` returns `None`, so capturing the return would have wrongly skipped every radical eval — trap avoided.)
  - `multi_docker_eval_adapter.py`: new `_agent_authored_dockerfile(agent, path)` = `path.exists() and getattr(agent,"configuration_success",False)`; `process_single_instance` guard swapped from `if dockerfile_path.exists():` to `if self._agent_authored_dockerfile(...)`, with a differentiated honest `else` (config-failed-with-repo-dockerfile vs no-dockerfile), both `skip_evaluation=True`.
- **Verification:** 3 new tests in `tests/test_adapter_logic.py` — **RED against pre-fix `b934412`** (helper undefined) → **GREEN**; full module 48 passed / 1 pre-existing django failure (unchanged). I personally reverted production to `b934412` and confirmed the RED, then restored. **5-repo metric impact: none expected** (ingestr scores 0 either way — laundered-broken before, honest-skip now); the value is honesty + protecting the wider-set A/B from laundered wins. **Process note: I caught the first opus root cause contradicting ground truth and sent it back before any code shipped — verify root cause against ground truth, not the report.**
- **Philosophy check:** ✅ REDUCES hollow success (removes a laundering path); raises the bar only for a negative outcome; arm-neutral; no done-gate/certify change.

### Change 3 — prefer the agent's successful by-name install over a fabricated failed editable  (`c57bd31`)
- **Observation:** pyads (the SWING repo) — agent configured the env in-sandbox (119/119 pass) via a SUCCESSFUL `pip install pyads` (ledger rc=0), but its editable `pip install -e .` FAILED (rc=1, meson/`src/pyads` missing). The eval recipe emitted the FAILED editable (`pip install -e . --no-deps`) so the fresh build crashed → honest 0, while radical scores pyads 1.0. Root cause (opus, pure-reproduced): `resolve_project_install` (`src/envstate/project_install.py:192`) FABRICATES `pip install -e .` whenever the project is in the closure + has packaging metadata — even when the agent's editable failed and a by-name install is what actually worked (`project_install_from_ledger` only counts rc==0 LOCAL installs, so it returned None).
- **Why:** the recipe must emit what the agent VERIFIABLY ended on. A by-name install the agent ran successfully (rc==0), pinned to the host-captured closure version, is the faithful project install; the fabricated failed editable is not. Host-grounded (ledger rc + pip-freeze version), no LLM, no eval relaxation.
- **What changed (`src/envstate/project_install.py` only, additive):** new `project_installed_by_name(ledger, project_name)` (rc==0 by-name install of THE PROJECT, anchored on the normalized project name so unrelated installs never match) + `_closure_project_pin(installed, project_name)` (`<name>==<ver>` from the closure Fact); a new guarded branch in `resolve_project_install` BETWEEN the ledger-cmd block and the editable fallback: if the project is in the closure AND a successful by-name install is recorded → emit `pip install <name>==<ver>` (finalized with `--no-deps`).
- **Verification:** 2 tests in `tests/test_project_install.py` — `..._prefers_successful_pypi_over_failed_editable` **RED against `33e69fe`** (emitted `pip install -e . --no-deps`) → **GREEN** (`pip install pyads==3.6.0 --no-deps`); over-match guard `..._does_not_overmatch_unrelated_failed_install` passes (a successful unrelated `pip install bar` does NOT change foo's editable fallback). Full module 17 passed (no regressions). I reverted prod to `33e69fe` and confirmed the RED myself. **Expected e2e impact: pyads flips fail→win → v1gsp 3 full_pass vs radical 2 → beats radical on rtpin_pilot5** (pending the e2e re-run).
- **Philosophy check:** ✅ emits only host-verified successful commands; additive (only fires when a successful by-name install exists); anchored on project name (no over-drop); no gate/certify change.
